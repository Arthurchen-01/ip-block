# EgressGuard · 零泄漏闸门

**一句话**：一个像 VPN 客户端一样有开关、有仪表盘的常驻闸门。它不允许**昆明 IP** 和**本机指纹**从这台机器泄漏出去——一旦发现，掐断，并且**明确告诉那个程序是因为这个原因被掐的**。

已打包成两个无黑框 exe，**目标机器不需要装 Python**：

```
dist\EgressGuardCore.exe   17.2 MB   守护进程（计划任务跑这个，常驻提权）
dist\EgressGuard.exe       17.2 MB   仪表盘（桌面快捷方式跑这个，普通权限）
```

---

## ⚠ 先说清楚它不是什么

**它不是 VPN，它不建立隧道。**

隧道由你已有的 iKuuu 客户端提供（本机实测：wintun 网卡 `iKuuuVPN`，`198.18.0.1/16`，出口 `103.151.172.36` / 香港 AS134972）。

EgressGuard 管的是**隧道之外的那一半**：流量绕过隧道的时候，是谁漏的、漏到哪去了、然后把它掐掉。这两件事必须分工，混在一起做会两边都做不好。

### exe 形态的实弹闭环（E5）取证

这一项最能说明问题。取证方式是**持久证据**，不是抢那一瞬间的连接状态：

```
（靶子连接在轮询窗口内已被守护掐掉，属正常 —— 见下面的持久证据）
[PASS] exe 守护在事件流里记录了对该程序的泄漏判定 — critical PHYSICAL_EGRESS
[PASS] 靶子通过内核连接表自检确认自己被掐断
       — [16:17:44] !!! 连接已被掐断 !!!  内核连接表里已经没有这条连接了。自检第 1 次
[PASS] exe 守护没有对 python.exe 做整程序封杀（防连坐） — 整程序隔离规则数=0
[PASS] 被掐程序能通过 /api/why 问到原因（不需要 token） — code=PHYSICAL_EGRESS
[PASS] 桌面原因卡已生成 — EgressGuard_已掐断_python.exe_0923_161750.txt
```

为什么不用"轮询连接表"取证：守护最快能在 SYN 到达后的 **250ms 内**就把 TCB 删掉，而靶子从启动到建连要 1 秒左右。实测出现过"建立与被掐都在同一秒内完成"，轮询窗口完全错过——**守护太快反而让测试失败**。所以改成查守护自己的事件流（事件不会一闪而过）+ 靶子自己的内核表自检日志 + `/api/why` 通道。

为什么 `/api/why` 和桌面卡也要轮询：通知通道要 spawn 子进程（控制台注入/事件日志/Toast），一次通知 5~8 秒。实测出现过"守护 16:05:58 就掐断了，通知文件 16:06:09 才写出来"。处置线程已加到 2 个来摊平并发，但测试仍然轮询而不是查一次就算。

## 隔离粒度：为什么默认是「程序→目标」而不是「程序」

这是被真实反馈打回来重做的设计。

**问题**：`python.exe`、`java.exe`、`node.exe`、`powershell.exe`、`svchost.exe` 这类是**共用宿主**——一个 exe 承载着无数互不相干的程序。按 exe 路径封杀整个程序，就会变成：

```
某个 python 脚本裸奔  →  这台机器上所有 python 程序一起断网
```

更糟的是：**源码形态下 EgressGuard 守护自己就跑在 `python.exe` 里**，它会把自己封杀，然后整机失去防护。

**修法**：默认隔离粒度降到 `(Program, RemoteAddress)`：

```
某个 python 脚本连 1.2.3.4 裸奔
  → 只封「python.exe 连 1.2.3.4」
  → 别的 python 程序连别的目标完全不受影响
```

实测验证（`tests/verify_no_collateral.py`）：

```
--- A. 对共用宿主的整程序封杀必须被拒绝 ---
  ok = False
  说明 = 拒绝：这是本工具自身（或它赖以运行的解释器）。封了它，守护进程会把自己一起封死。

--- B. 对共用宿主的【目标级】封杀应该成功（新的默认动作）---
  ok = True
  说明 = 已封杀 python.exe 连 203.0.113.7（只封这一个目标，不连坐）

--- C. 规则真的建出来了，而且只封了那一个目标 ---
  {"Name":"EgressGuard::TARGET::python.exe::203_0_113_7","Action":"Block",
   "Remote":"203.0.113.7","Program":"...\\Python312\\python.exe"}

--- D. 惯犯升级：普通程序封满 8 个目标才升级；python 永不升级 ---
  普通程序（已封 9 个目标）: escalate=True
  python.exe（已封 9 个目标）: escalate=False  理由=是本工具自身，永不升级
```

三层防护：
1. **默认**：只封「程序→目标」，连坐面几乎为零
2. **升级**：同一个程序被封目标数达阈值（默认 8）才升级成整程序封杀——此时它已被证实是惯犯
3. **例外**：共用宿主（40 个名单）与工具自身**永不升级**，无论封了多少目标

## 关于「发现流量问题就转到 iKuuu / VPN 出口」

这个诉求是对的。我把答案**实测**出来了，不是推测 —— 见 `tests/exp_guide_to_tunnel.py`。

### 实测结果

| 情况 | 实验 | 结果 |
|---|---|---|
| **A. 程序按路由表走** | 加一条主机路由把 `203.0.113.7` 指向物理网卡 → 连接源地址变成 `192.168.0.101`（裸奔）；**删掉那条路由** → 重连 → **源地址变成 `198.18.0.1`** | ✅ **可引导回隧道** |
| **B. 程序显式 bind 物理网卡** | 路由明明指向隧道，源地址仍是 `192.168.0.101` | ❌ **用户态无法改道** |
| **C. 你机器上的真实裸奔目标** | `27.44.127.109`、`47.104.208.14` 的**路由判定本来就是 iKuuuVPN** | 说明它们是**显式 bind** 出去的 → 属于 B |

### 结论

**「把一条已经建立的裸奔连接转到 VPN 出口」做不到。** 那条连接显式绑定了物理网卡，根本不进 TUN。要改道需要 WFP 重定向或 TUN 驱动层面的支持——用户态没有任何 API 能做到。任何声称能"把已建立的连接转进隧道"的工具，要么在骗你，要么它自己就是驱动。

**但有两件真正能做到的引导，而且都做进去了：**

**① 删掉让它绕过隧道的路由 —— 这是唯一真正能"导回 VPN 出口"的手段**

实测有效：删掉那条指向物理网卡的主机路由后，按路由表走的程序重连时源地址会变成隧道地址，**出口就变成 VPN 落地了**。

仪表盘上两个按钮：「查绕过隧道的路由」+「清掉绕过路由（导回隧道）」。

启动自检还会自动清理一类**必然是脏状态**的路由：把**隧道段地址**（`198.18.0.0/15`）指向物理网卡的路由。实测真的抓到过一条（`198.18.0.107/32 → WLAN 3`，早期测试崩溃留下的）——它把本该进隧道的 fake-IP 流量送到了物理网卡上，等于凭空造出一条泄漏路径。

**② 掐断 → 逼它重连 —— 这本身就是最有效的引导**

程序重连时如果不显式 `bind` 物理网卡，Windows 就会按路由表把它送进 TUN，**自然就进隧道了**。

也就是说：**掐断不是"惩罚"，是"把程序推回正常路径"**。实测里那条 `WinError 10053`（本机软件中止了已建立的连接）就是这个含义——程序被推回去重连了。

**③ 把系统代理指向隧道端口**（补充手段）

支持系统代理（WinINET）的程序——浏览器、一部分客户端——会主动走隧道。仪表盘上「探测隧道代理端口」+「引导系统代理到隧道」做这件事。

生效范围：浏览器、任何读系统代理的程序。
不生效：自己管网络栈的程序（多数国产 IM、游戏、以及显式绑网卡的程序）。

**你的代理连接本来就自动走隧道，这一点实测确认过**：iKuuu 的 TUN 把域名解析成 fake-ip（`www.baidu.com` → `198.18.0.107`），网络层就塞进隧道了，`LocalAddr = 198.18.0.1`。真正需要 EgressGuard 管的是那些**绕过隧道裸奔**的程序（钉钉、svchost、系统 DNS），那不是你的问题，是它们的问题。

## 它到底在防什么

### 五类泄漏，五个判据

| # | 泄漏类型 | 判据 | 严重度 |
|---|---|---|---|
| 1 | **裸奔出站** | 连接的 `LocalAddr` 落在**物理网卡 IP 集合**里 → 这条连接没走隧道，对方看到的是你的真实地址 | critical |
| 2 | **出口 IP 是昆明/大陆** | 主动探测出口 IP + 地理/ASN 查询，命中云南段/大陆/标定的本机真实出口 | critical |
| 3 | **IPv6 旁路** | 非隧道网卡上存在**全局 IPv6 地址**且有 `::/0` 默认路由 | high |
| 4 | **DNS 泄漏** | 非隧道网卡上配置了非隧道 DNS 解析器 | high |
| 5 | **指纹外发** | ① NetBIOS / mDNS / LLMNR / SMB / SSDP / WS-Discovery 等会广播主机名的协议；② 出站内容里出现主机名 / MAC / MachineGuid / 主板 UUID / 用户名 | critical |

### 判据 1 为什么不能用路由表

这是本项目最关键的技术事实，写在这里是因为**几乎所有人第一次都会做错**：

> Windows 上判断"一条连接走没走隧道"，**不能用 `Find-NetRoute` / `GetBestRoute`**。
> TUN 型代理会把 `0.0.0.0/0` 整条劫持到隧道上，于是路由表查询会对"代理自己绑定物理网卡
> 去连上游服务器"的连接也回答"走隧道"，给出**完全相反**的结论。
>
> 唯一权威的判据是 `GetExtendedTcpTable` 的 **`dwLocalAddr`**——这条连接真正绑定在哪个本地 IP 上：
> - `LocalAddr = 198.18.0.1` → 进了隧道
> - `LocalAddr = 192.168.0.101` → **裸奔**

本机实测（同一时刻）：

```
pid=  9104 192.168.0.101:49747 -> 27.44.127.109:808   ESTAB   ← 隧道自身外层传输，必须放行
pid=  6884 192.168.0.101:61006 -> 4.145.79.80:443     ESTAB   ← 真泄漏：svchost 直连 Azure
pid= 27004 192.168.0.101:64871 -> 116.132.235.207:443 ESTAB   ← 真泄漏：钉钉绕过隧道
pid=  6408 198.18.0.1:49317   -> 202.79.172.190:6794  ESTAB   ← 正常，在隧道里
```

### 定级：三档，不是两档

| 连接状态 | 定级 | 可处置 | 理由 |
|---|---|---|---|
| ESTAB / SYN_SENT / SYN_RCVD | critical | ✅ | 正在传数据，真在漏 |
| **CLOSE_WAIT** | **high** | **✅** | 对端关了但**本地 socket 还开着**，程序仍可写入。更重要的是：**快泄漏常只能抓到这一帧**，判成不可处置就等于对快泄漏完全瞎掉 |
| TIME_WAIT / FIN_WAIT / LAST_ACK | low | ❌ | 纯历史痕迹。TIME_WAIT 数量极大（隧道自身连接结束后都落这里），必须压到最低档 |

### 为什么守护用「当前用户 + Highest + S4U」而不是 SYSTEM

| 方案 | 能改防火墙？ | 通知能到你桌面？ |
|---|---|---|
| SYSTEM 身份 | ✅ | ❌ 跑在会话 0，弹窗/桌面原因卡/Toast **全都送不到你的桌面** |
| 当前用户 + Highest + S4U | ✅ 提权令牌，不弹 UAC | ✅ 跑在你自己的会话里 |

本工具的核心功能就是「告诉那个程序为什么被掐」——用 SYSTEM 的话这个功能直接不存在。

### 使用节奏（重要，别跳）

```
观察档（默认）  enabled=false                只记录、只报告，不动任何连接
   ↓  先跑几分钟，看判定有没有误报
演练档          enabled=true, dry_run=true   判定 + 通知，但仍不动连接
   ↓  再确认一轮
实弹档          enabled=true, dry_run=false  判定 + 通知 + 掐断 + 隔离
```

**为什么默认是观察档**：这类工具最危险的失败模式是"误判把正常网络掐了"。先让判定跑给你看，确认它认得出真泄漏、也不乱咬，再上实弹。

## 处置动作（四档）

| 档位 | 行为 |
|---|---|
| `notify_only` | 只记录 + 通知（演练模式强制此档） |
| `block_new` | 防火墙规则封杀该程序后续出站 |
| `block_and_kill` | 上面 + `SetTcpEntry(DELETE_TCB)` **强杀已建立的 TCP 连接**（推荐） |
| `block_kill_proc` | 上面全部 + `taskkill /T /F` 终结违规进程（最狠） |

`SetTcpEntry` 是 Windows 上唯一能在用户态真正掐断一条已建立连接的手段。IPv6 连接和 UDP 不支持强杀，靠防火墙规则阻断——这是平台限制，工具里明确说明了，没有假装能办到。

### 隧道断开自动熔断（推荐开，默认开）

隧道在的时候正常跑；隧道一断，立刻把出站默认策略切成 Block，只放行隧道程序（好让它重连）+ 本工具自身。**这才是 kill switch 真正有价值的用法**：消灭"VPN 掉了、流量裸奔"那个窗口，而不是长期全局拒绝。隧道恢复后自动解除。

## 给集成方：怎么判断闸门状态

**不要只看 HTTP 通不通** —— 那分不清"闸门没装"和"闸门正在重启"。

一条命令搞定：

```bash
EgressGuardCore.exe --check          # 打包形态
python run_core.py --check           # 源码形态
闸门状态.bat                          # 双击
```

```jsonc
// 运行中
{ "status": "running", "alive": true, "message": "闸门运行中（已运行 14.0 秒）",
  "status_detail": { /* 完整状态，省一次 /api/status 调用 */ } }

// 正在重启（这是关键的一种，以前分不出来）
{ "status": "restarting", "alive": false, "heartbeat_age_s": 8.5,
  "message": "闸门正在重启（心跳 8 秒前，仍新鲜）—— 不是没装",
  "advice": "等几秒重试；守护由计划任务拉起，通常 10 秒内回来" }

// 被主动停掉了
{ "status": "stopped", "alive": false,
  "message": "闸门被主动停掉了（2026-09-23 20:03:37）" }

// 没在跑（没装 or 崩了很久）
{ "status": "not_running", "alive": false,
  "message": "闸门没在跑（也没有任何历史状态文件 —— 多半是没装过）",
  "advice": "要装：双击 安装_右键管理员运行.bat" }
```

判定逻辑固化在 `probe_gateway()` 里，你也可以自己读心跳文件：

```
%LOCALAPPDATA%\EgressGuard\state.json
  last_heartbeat 在 30 秒内  ->  守护活着（或正在重启）
  state == "stopped"          ->  被人主动停掉了
  文件不存在 / 心跳过期        ->  没在跑
```

守护每 5 秒原子写一次心跳（临时文件 + `os.replace`），主动退出时会写 `state: "stopped"`，
被强杀则只会让心跳变旧 —— 两种情况集成方都能区分。

## 诚实的局限

1. **UDP 出站的目的地址看不到。** Windows 的 `GetExtendedUdpTable` 不记录远端，所以 UDP 泄漏只能靠"本地地址绑定物理网卡"间接判断，拿不到对端是谁。
2. **HTTPS 载荷里的指纹看不到。** 内容指纹扫描对明文 HTTP 有效；HTTPS 需要 MITM 证书，本工具**没有**内置（装根证书的风险大于它挡住的泄漏）。真正干活的是前四条结构性判据。
3. **提权进程的 exe 路径需要提权才能读到。** 装上计划任务后守护是提权的，路径能拿到；以普通权限手动跑时拿不到，此时工具会明说"拿不到路径，跳过隔离"。
4. **地理判定依赖第三方库**（ip-api / ipwho.is / ip.sb）。三个都不可用时会明确报"查询失败"，不瞎猜。主力判据（本地地址绑定物理网卡）完全不依赖它们，是本机事实。
5. **网卡态势刷新约 5~6 秒**（PowerShell 启动 + CIM 模块加载的固定成本，不是命令条数的问题）。它跑在独立线程不阻塞热循环，但网络拓扑变化最多 20 秒后才被反映。
6. **严格 kill switch（全局默认拒绝）默认关闭。** 打开后不在白名单里的程序会全部断网。默认关，需要时在配置里开。
7. **隧道自身的外层流量会被放行。** 本机实测 iKuuu 客户端自己会从物理网卡连 `27.44.127.109:808`（隧道入口）和几个国内 DNS（`223.5.5.5` / `1.12.12.12` / `120.53.53.53`）。这些**必须**放行，否则闸门会把 VPN 自己掐死、然后整机断网。仪表盘连接表里把它们标成「隧道外层(放行)」，你能看到 VPN 客户端到底在跟谁说话。

## 测试怎么做才安全

任何会动防火墙的实验之前，先装一个「**死亡开关**」：一个 N 分钟后无条件恢复网络的计划任务（SYSTEM 身份）。实验正常结束就撤掉它；脚本崩了它也会兜底。

```powershell
# tests/acceptance.py 里的做法
arm_deadman(4)        # 装：4 分钟后无条件恢复网络
... 做实验 ...
disarm_deadman()      # 撤
```

收尾统一清理，且清理本身也包了异常处理：撤死亡开关 → 删测试路由 → 清 EgressGuard 规则 → 恢复防火墙基线。**清理失败只告警，不会掩盖原始错误，也不会带着脏状态退出。**

### 怎么可控地制造一个真实泄漏

隧道劫持了默认路由，所以直接绑物理网卡连外网会被丢包。做法是加一条**主机路由**，把某个真实 IP 精确地赶出隧道：

```powershell
route add 218.30.118.6 mask 255.255.255.255 192.168.0.1 metric 1 if 24
```

然后靶子程序 `bind(192.168.0.101)` 去连它 —— 内核连接表里就出现一条 `LocalAddr = 192.168.0.101` 的连接，正是真实泄漏的形态。实验后 `route delete` 即可，完全可逆。

靶子自己**查内核连接表**来判断有没有被掐（`SetTcpEntry` 一执行，那一行就消失）——这是最硬的判据。早期版本用 `sendall(b"")` 探活是错的：零字节 send 是空操作，永远不报错。

## 出问题了怎么办

**网络被锁死了** → 双击 `紧急恢复网络_右键管理员运行.bat`。出站策略回 `Allow`、删掉全部 EgressGuard 规则、停掉计划任务。不删数据，恢复后可以重装。

**怀疑误报** → 打开仪表盘「实时连接」，看被标成「裸奔泄漏」的行。如果那个程序**确实**在绕过隧道，那不是误报；如果不该拦，把它的 exe 名加进白名单。

**守护没反应** → 先跑 `闸门状态.bat`（或 `EgressGuardCore.exe --check`）它会直接告诉你闸门是「运行中 / 正在重启 / 已停止 / 未运行」。再看 `%LOCALAPPDATA%\EgressGuard\events.jsonl` 最后几行。守护启动时先起 API 再刷网卡，所以启动后头几秒 API 响应了但网卡信息是空的，这是正常的。

**想看它到底拦了什么** → `%LOCALAPPDATA%\EgressGuard\events.jsonl`，每行一个 JSON；或者桌面上那些 `EgressGuard_已掐断_*.txt`。
